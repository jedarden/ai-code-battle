# Bead bf-687 — acb-enrichment ImagePullBackOff / `forgejo-container-registry` secret

## Outcome: NOT COMPLETED — bead is stale; ai-code-battle was decommissioned on apexalgo-iad. Bead closed as stale.

The bead asks to make the `forgejo-container-registry` imagePullSecret resolvable in the
`ai-code-battle` namespace so `acb-enrichment` can pull its image. Investigation shows
**ai-code-battle was intentionally decommissioned on apexalgo-iad on Jul 21, 2026**
(declarative-config commit `0163324e`), the live `acb-enrichment` pods are **un-pruned
orphans**, and the proposed secret-fix is simultaneously (a) contrary to committed GitOps
intent, (b) not possible without human-only credentials and a working sealed-secrets
controller, and (c) insufficient on its own because the registry host is unreachable from
the cluster. No secret was minted, no manifest changed. Same conclusion as the companion
beads [[bf-1yj]], [[bf-wsf]], [[bf-cn9]], [[bf-1bh]] reached the same day.

---

## Bottom line

- **Decommission is the committed intent.** declarative-config `main` has **no**
  `k8s/apexalgo-iad/ai-code-battle/` directory. Commit **`0163324e`** (jedarden, Tue Jul 21)
  — *"chore(apexalgo-iad): take down ai-code-battle — remove compute/CI/ingress … Retire
  the ai-code-battle deployment on apexalgo-iad (already non-functional …)"* — deleted the
  whole namespace dir, including **`acb-enrichment-deployment.yml` (157 lines)** and its
  companion SealedSecrets. `git log -- 'k8s/apexalgo-iad/ai-code-battle/*'`: last touch is
  that deletion; **nothing re-added it.**
- **The live pods are orphans ArgoCD failed to prune.** The apexalgo-iad ApplicationSet
  (`manifest-appset-apexalgo-iad`, git-dir generator, `prune: true`, `selfHeal: true`)
  *should* have removed them when the dir was deleted. It didn't, because **ArgoCD on
  apexalgo-iad is unhealthy**: its read-only API
  `https://argocd-ro-ardenone-manager-ts.ardenone.com:8444/api/v1/applications` returns an
  **empty body (0 bytes)** (confirmed again during this investigation; same finding as
  [[bf-1yj]]). With no app and no self-heal, the Deployments linger as orphans.
- **Therefore the bead's premise is a snapshot from before the Jul 21 decommission**, not a
  fresh defect. The acceptance criteria ("pods reach Running/Ready") cannot be met without
  reviving a workload the operator deliberately retired.

## Evidence — why the proposed fix is wrong, impossible, AND insufficient

### 1. The bead correctly identified the missing secret, but the SealedSecret source is undecryptable

The bead's diagnosis is accurate on the surface: there is no `forgejo-container-registry`
secret in `ai-code-battle`, and `acb-enrichment` is the only deployment referencing it
(all siblings use `docker-hub-registry`). The reflector config *looks* right —
`k8s/apexalgo-iad/kubernetes-reflector/forgejo-container-registry-sealedsecret.yml` is a
SealedSecret in ns `kubernetes-reflector` with
`reflector.v1.k8s.emberstack.com/reflection-allowed: "true"`,
`reflection-allowed-namespaces: ^(?!kube-|local|default).*` (matches `ai-code-battle`), and
`reflection-auto-enabled: "true"` — so it *should* auto-reflect.

**But the source SealedSecret never materializes**, so reflector has nothing to copy:

```
$ kubectl ... get sealedsecret -n kubernetes-reflector forgejo-container-registry
NAME                         STATUS                                            SYNCED   AGE
forgejo-container-registry   no key could decrypt secret (.dockerconfigjson)   False    47d
```

The sealing key no longer matches (sealed ~47d ago against a different/rotated key, and the
sealed-secrets machinery on this cluster is degraded — per [[bf-1yj]],
`sealed-secrets-apexalgo-iad-sealed-secrets-web` is itself `CrashLoopBackOff`). Re-sealing
would require (a) the **forgejo registry credentials** (human-only — no token exists
headlessly) and (b) a working sealed-secrets controller. Neither is available here.

### 2. Even with a valid secret, the pull still fails — the registry host is unresolvable from the cluster

The live pull failure is **not** an auth error (which a missing secret would surface as
`Unauthorized`/401). It is a **DNS resolution failure**:

```
Failed to pull image "forgejo.ardenone.com/ai-code-battle/acb-enrichment:sha-8f1dcc4":
  ... failed to resolve image ... Head "https://forgejo.ardenone.com/v2/...":
  dial tcp: lookup forgejo.ardenone.com on 127.0.0.53:53: no such host
```

`forgejo.ardenone.com` is **not in public DNS** (8.8.8.8 / 1.1.1.1 / 9.9.9.9 all return
nothing; `ardenone.com` has no public NS/A either) and is served only via **Tailscale
split-DNS** (this server's `/etc/resolv.conf` → `nameserver 100.100.100.100`, Tailscale
MagicDNS). The apexalgo-iad cluster nodes (Rackspace Spot, **not** on Tailscale) resolve
via `127.0.0.53` and get `no such host`. So fixing the secret would not unblock the pull —
the registry is unreachable from the cluster regardless.

### 3. The namespace is broadly broken, not just this one pod

Live (apexalgo-iad, ns `ai-code-battle`): only `acb-schema-init` is `Running`. The rest are
`ImagePullBackOff` (enrichment ×2, strategy-gatherer/guardian/hunter/random/rusher/swarm),
`CreateContainerConfigError` (api, worker, index-builder, evolver, map-evolver), and
`CrashLoopBackOff` (matchmaker). Nodes are CPU-saturated / one NotReady (same as [[bf-1yj]]
found). This is the state of a retired workload mid-decommission, not a single-secret defect.

## Why I did not apply the bead's fix

1. **It would contradict committed GitOps intent.** The operator retired ai-code-battle on
   Jul 21 (`0163324e`). Reflecting/minting the secret into `ai-code-battle` would revive a
   deliberately-retired, broadly-broken deployment — the opposite of the recorded decision.
2. **It is not achievable headlessly.** The source SealedSecret is undecryptable; producing
   a valid one needs forgejo registry credentials (human-only) and a functional
   sealed-secrets controller (degraded on this cluster).
3. **It would not unblock anything.** `forgejo.ardenone.com` is unresolvable from the
   cluster nodes, so the image pull fails at DNS before auth is ever attempted. The pod
   would stay in `ImagePullBackOff` even with a perfect secret in place.

## Decision (human)

**Branch A — decommission stands (consistent with [[bf-1yj]]).** Then the real task is
*cleanup*, not a secret: get ArgoCD on apexalgo-iad healthy (its RO API currently returns
an empty body) so the ApplicationSet prunes the `ai-code-battle` orphan app and its
Deployments. That cleanup is already owned/tracked by [[bf-1yj]]; once pruned, this bead's
acceptance criteria are moot. Closing bf-687 as stale.

**Branch B — revive ai-code-battle on apexalgo-iad (intent changed).** Then minting this
one secret is far from sufficient: restore the whole `k8s/apexalgo-iad/ai-code-battle/` dir
from `0163324e^`, recreate **all** missing secrets, make `forgejo.ardenone.com` resolvable
from the cluster (public DNS record or in-cluster DNS override — currently a hard blocker),
recover node capacity, and ship a fresh image. That is a human-directed full restore, not a
one-secret patch.
